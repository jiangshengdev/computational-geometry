## 脚本语言

- 尽可能使用 TypeScript（`.ts`），而不是 `.mjs`；仅在现有运行环境或工具明确不支持时使用 `.mjs`，并说明原因。

## Rust 编码与 API

- 使用 `format!` 时，在可能的情况下将变量内联到 `{}` 中；合并可合并的 `if`，使用方法引用代替冗余闭包。遵循对应的 Clippy 建议，仅处理当前修改范围，不为统一写法开展全仓清理。
- 避免含义不明的 `bool` 或 `Option` 位置参数，优先使用枚举、具名方法或 newtype，让调用点自行表达含义；不禁止语义明确的布尔参数。
- 尽可能穷尽 `match` 的领域状态，避免用通配分支掩盖新增状态所需的处理。
- 新增 trait 必须有文档注释，说明职责及实现方应遵守的契约；不为满足本规则主动引入 trait。
- 优先使用私有模块，并显式导出 crate 的公共 API。不得仅为方便测试而扩大生产 API 的可见范围或增加公共辅助函数。

## 模块与变更组织

- 根据职责、状态所有权、变化原因和调用关系判断是否拆分模块；文件长度和 diff 行数只作为调查信号，不作为自动拆分、停止或扩大重构范围的门禁。
- 提取模块时，将维护同一不变量的相关测试、模块文档和类型文档放在实现附近；遵守当前任务的重构范围，不仅为组织形式搬迁已有代码。
- 避免没有可读性或封装收益的碎片化辅助函数；只调用一次不构成禁止提取的理由，清晰的领域操作仍可独立封装。

## 组件与库复用

- 实现或修改功能前，必须检查项目已有组件、封装和已引入库的能力；已有能力能够满足需求时，必须复用，禁止重复手写同一能力。
