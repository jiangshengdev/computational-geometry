## 测试范围

- 默认不执行全量测试，只执行与本次变更影响相关的必要测试。
- 添加测试必须谨慎，非必要不加测试；禁止为了方便验证、凑覆盖率或流程完整而随意添加测试。新增前必须检查已有覆盖，明确尚未覆盖的功能风险及新增测试的必要性；已有测试足以验证时应复用，不得重复添加。

## 测试编写与验证

- 算法公开 API 的功能与性能测试使用独立目录，并镜像实现目录：`src/algorithms/<algorithm>/` 对应 `tests/algorithms/<algorithm>/`。算法测试文件不得直接放在仓库根目录或顶层 `tests/`，已有算法测试也须遵循此布局。
- 嵌套目录中的 Rust 算法测试通过 `Cargo.toml` 的 `[[test]]` 显式注册，保持从 crate 公开 API 验证行为，不为目录迁移扩大内部 API 可见性。迁移保留测试名称与行为。
- 源码内部验证私有行为的单元测试遵循下述同级测试模块约定；HTTP、流协议及共享校验等非算法测试按所属职责组织，不机械归入某个算法目录。
- 当整个对象均属于被验证的契约时，优先比较整个对象；只验证局部契约时，不将无关字段锁入断言，也不为改善断言输出引入新依赖。
- 不添加仅复述静态定义或检查某段实现是否存在、是否被删除的测试；必要的功能不变量和禁止行为仍应验证。
- 避免在测试中修改进程全局环境，优先显式传入配置或依赖。确需验证环境变量读取时，使用隔离的子进程，避免影响并行测试。
- 新增 Rust 测试模块时，将内容放入独立的同级文件，并使用显式的 `#[path = "..._tests.rs"]` 引入；不为遵循此约定搬迁或重写已有内联测试模块。
- 按功能风险选择测试层次：精确几何逻辑使用算法测试，HTTP 和流协议使用公共接口集成测试，用户交互使用 E2E。复用已有覆盖，不要求每次变更新增集成测试；跨层测试继续遵守根目录独立编排要求。
- 纯格式化不重复运行已有效通过的测试；自动修复若改变行为，则运行受影响的必要测试，不把修复前的结果视为修复后的行为验证。
